# Markdown Reader

轻量、快速的本地 Markdown 阅读器 Chrome 扩展（Manifest V3）。

## 开发

```bash
npm install
npm run dev      # 监听构建到 dist/
npm run build    # 生产构建（含类型检查）
npm run verify   # 类型检查 + ESLint + 单元测试
```

加载到浏览器：`chrome://extensions` → 打开「开发者模式」→「加载已解压的扩展程序」→ 选择 `dist/`。

`fixtures/sample.md` 是覆盖全部支持语法的手工验证文档，把它拖进阅读器窗口即可查看渲染效果。

```
 ├ stores       Zustand 状态（settings / ui / document）
 ├ search       全文搜索：文本匹配与 Highlight API 绘制
 ├ export       导出：HTML 快照 / Markdown 规整 / PDF 打印
 ├ themes       阅读主题注册表与预设
 ├ markdown     渲染管线（契约已定，Phase 2 实现）
 ├ plugins      Markdown 插件注册表
 ├ styles       设计令牌与全局样式
 ├ utils        存储、消息、函数工具
 ├ types        全局类型定义
 └ assets       静态资源
```

## 在浏览器里直接打开 .md

装好扩展后，双击本地 `.md` 文件或访问一个 `.md` 地址，页面会自动被阅读器接管，
**地址栏保持不变**（仍是 `file:///…/xxx.md#某标题`），带锚点打开会直接跳到对应章节。

本地文件需要额外授权一次：`chrome://extensions` → 本扩展 → 打开「允许访问文件网址」。
不想要这个行为可以在「设置 → 高级 → 接管浏览器打开的 .md」里关掉。

不生效的两种情况：服务器给 `.md` 带了 `Content-Disposition: attachment`（浏览器
直接下载，页面根本没打开）；或地址带查询串（`x.md?v=1`，不在匹配范围内）。
这两种都可以用工具栏的「打开文件」正常阅读。

### 接管页面里的功能差异

阅读器在接管页面里是嵌在 `file://` 页面中的 `chrome-extension://` iframe，
属于**第三方 iframe**，浏览器禁止这类 iframe 弹出任何文件选择器
（`Third party iframes are not allowed to show a file picker`）。因此：

| 动作 | 接管页面里的行为 |
| --- | --- |
| 打开文件 | 退到 `<input type="file">`，可用，但该文档不支持自动刷新 |
| 打开文件夹 | 由宿主页面代劳（见下），可用 |
| 导出 HTML / Markdown | 退到浏览器下载，文件落在下载目录 |
| 打印 / 导出 PDF | 不受影响 |

**文件夹的代理机制**：iframe 把「请弹目录选择器」发给宿主页面，宿主是顶层帧、
没有这条限制，而用户在 iframe 里的点击会把短暂用户激活一并传播给祖先帧，
所以宿主收到消息时仍握着有效手势。宿主自己扫描目录，只把**纯数据**的文件树
发回来；点开某个文件时同样由宿主读取内容再回传。

刻意不把目录句柄 postMessage 过去：文件系统权限按源授予，句柄跨到
`chrome-extension://` 就成了一个没有权限的对象，需要重新授权，
而那一侧恰恰弹不出授权框。让数据过界、句柄留在原地，才是走得通的那条路。
代价是句柄无法持久化（`file://` 页面没有可用的持久存储），
所以接管页面里每次都要选一次目录；独立标签页里则是选一次就长期记住。

选择器的起始位置做了两层：第一次从文件路径认出所属的知名目录
（`~/Downloads`、`~/Documents` 等，浏览器只接受这几个常量，不收任意路径），
之后靠固定的选择器 `id` 让浏览器记住上次选中的目录——从第二次起就直接停在那里。

### 自动列出所在目录

接管页面打开后，侧栏文件树会**自动列出该文档所在的目录**，不需要点任何东西，
刷新也照样在。走的不是 File System Access API，而是直接读 `file://` 地址：
扩展声明了 `file:///*` 主机权限，配合用户勾选的「允许访问文件网址」，
就能读取目录列表页并解析出条目。

为什么不用文件选择器：`showDirectoryPicker` 的 `startIn` 只接受几个知名目录
常量或一个已有句柄，**给不了任意路径**，所以第一次永远落不到目标目录；
而目录句柄又无法在 `file://` 页面里持久化，每次刷新都要重选。
这两条都是规范层面的限制。直接读地址则完全绕开了句柄与授权框。

读不到时（没开文件访问权限，或浏览器改了目录列表格式）安静回退到
「打开文件夹」的手动引导，功能不会整个失效。

### 关于独立标签页里的「自动加载所在目录」

侧栏文件树**不能**在打开某个 `.md` 时自动列出它的上一级目录——这是
File System Access API 的硬约束：既无法从文件句柄取到父目录，目录选择器
也必须由用户手势触发。

能做到的是把代价压缩到一次：文件树的按钮会直接写出目录名（如「打开「docs」文件夹」），
选择器也会停在当前文件所在的位置；确认之后句柄存进 IndexedDB，
此后打开该目录下的任何 `.md`（包括接管页面）都会自动带出文件树，不再需要点击。
授权在浏览器重启后会降级，届时面板会再给出一次确认按钮。

## 关键设计

- **构建**：不用 CRXJS 之类的封装插件，`manifest.json` 由 `public/` 原样拷贝，产物路径完全可控。
- **存储分区**：小配置走 `chrome.storage.sync`（跨设备同步），自定义 CSS/JS 等大字段走 `local`，绕开 sync 单条 8KB 的配额上限。
- **主题**：所有主题差异收敛为 CSS 变量，切换只改根节点 `data-theme`，不触发任何组件重渲染。
  「明暗模式」与「阅读主题」是两个正交维度：前者决定 `data-theme`，后者从
  `themeRegistry` 取一套令牌覆盖，二者可自由组合（护眼纸张也有深色版）。
- **样式层级由顺序决定**：基础令牌（theme.css）→ 阅读主题（`<style id="app-theme">`）
  → 用户 CSS（`<style id="user-style">`），三层的令牌选择器一律写成
  `:root:where([data-theme='…'])` 把特异度压到 (0,0,1)，胜负只看在 `<head>` 里的先后。
  插入顺序由 `utils/style-slots.ts` 固化，不依赖 hook 的调用次序。
  打印样式是唯一的例外，它刻意用裸属性选择器高出一档，保证任何主题都打成黑字白底。
- **插件化**：渲染能力全部通过 `pluginRegistry.register()` 接入，新增 PlantUML / ECharts 等无需改动核心渲染器。
- **语法高亮不碰 WASM**：Shiki 默认用 Oniguruma 正则引擎，它是一份 WASM，
  而 MV3 扩展页面的 CSP 固定为 `script-src 'self'`，实例化 WASM 需要
  `wasm-unsafe-eval`——为了语法高亮放宽整个页面的脚本策略不划算。
  改用 JS 正则引擎（把 Oniguruma 模式转译成原生 RegExp），顺带省掉 600KB 的
  wasm 分包；`forgiving` 让极少数转译不了的模式被跳过而不是整个语言失败。
- **管线按需加载**：markdown-it + 全部插件 + KaTeX + DOMPurify 近 500KB，全部走动态 import，
  只有真正打开文档时才下载。Shiki 语法与 Mermaid 再下沉一层，按文档实际用到的语言/图表加载。
- **净化在出口**：所有插件产出的 HTML 统一过一次 DOMPurify（`sanitizeHtml`），
  插件作者不需要各自考虑 XSS。这也是整条管线里唯一的 HTML 注入点，便于审计。
- **句柄不进 store，路径进 store**：文件句柄不可序列化，只存在模块级登记表里；
  但「这条历史记录还能不能点开」是实打实的界面状态，因此把可用路径集合放进
  store，UI 从状态推导而不是去读一个不会触发重渲染的全局 Map。
- **阅读位置按锚点定位**：记录「视口上方最近的标题 + 相对它的像素偏移」，
  而不是纯滚动比例。自动刷新时文档上方常有内容增删，比例定位必然漂移。
- **增强器按维度幂等**：DOM 增强（Shiki 上色、Mermaid 出图）各自记录已应用的
  配色/折叠策略，只有真正变化的维度会重做。既保证设置「修改立即生效」，
  也不会因为调一下字号就把用户手动展开的代码块折叠回去。
- **设置表单只写一份**：阅读器抽屉与独立设置页（options.html）共用 `SettingsPanel`，
  容器差异留给各自宿主。
- **工具栏动作即数据**：按钮、窄窗口的「更多」菜单、全局快捷键三处共用
  `useToolbarActions()` 产出的同一份声明，新增动作只改一处，也不会出现
  「按钮已置灰、快捷键还在拦截浏览器默认行为」这类不一致。
- **页面接管用 iframe 而不是注入或重定向**：内容脚本是普通脚本，不支持 `import()`，
  而整条渲染管线全靠动态导入按需加载，注入进去就得全量打包；重定向到
  `viewer.html?src=…` 则会把地址栏换成 `chrome-extension://`，书签、分享的链接、
  文档里的相对链接全部失效。换成一个指向 `viewer.html` 的全屏 iframe，
  地址栏原样保留，阅读器也不必为「页面内」维护第二条代码路径。
  源文本直接取自浏览器已经渲染出的 `<pre>`，因此不需要任何主机权限。
- **分块发生在解析之前**：实测 10MB 文档一次渲染 7.5s，其中 `md.parse()` 独占
  85%。token 级分块必须先解析完整篇，那 85% 一秒都省不掉，所以切的是**源文本**。
  切点只落在标题或安全的空行处，绝不切进围栏代码块或列表中间。
  意外收获是 markdown-it 在超大字符串上是超线性的，切开之后解析总耗时反而降了。
- **分块粒度是量出来的**：`md.parse()` 与 DOMPurify 都有可观的每次调用固定开销，
  块切得越碎乘的次数越多。64KB 时 1MB 文档的净化总耗时从 90ms 涨到近 700ms，
  128KB 才是平衡点。
- **让步用 MessageChannel 而不是 `scheduler.yield()`**：后者的续体优先级更高，
  会插到 React 的渲染提交（同样走 MessageChannel）前面，结果是分块循环一路
  跑完、所有块最后一起出现——分块照做了，首屏反而更慢。
- **昂贵的增强按需触发**：10MB 文档有六千多个代码块，全量上色是二十多秒纯计算，
  而绝大多数用户永远不会滚到。改由 IntersectionObserver 驱动，只处理视口上下
  各两屏内的块。观察器的 root 必须设成滚动容器——`rootMargin` 撑不开中间那层
  `overflow: auto` 的裁剪，用默认视口会导致折叠线以下永远等不到上色。
- **搜索不改 DOM**：命中处用 CSS Custom Highlight API 绘制，而不是插 `<mark>`。
  插标签意味着每改一次查询词就要切开再合并成百上千个文本节点，
  33 万节点的文档会被反复重排。
- **导出快照屏幕而非重跑管线**：屏幕上的 DOM 才是完整成品（Shiki 已上色、
  Mermaid 已出图、KaTeX 已展开），重跑一遍不但慢，任何实现漂移都会让
  「导出的样子」和「看到的样子」对不上。样式同理，直接读 CSSOM 而不是
  手写一份导出专用样式——后者一定会随 markdown.css 的改动而失效，且无从察觉。
- **PDF 走浏览器打印管线**：不引入 jsPDF / html2canvas（近 1MB，且是先截图再嵌入，
  文字发虚）。浏览器打印输出矢量文字，`break-inside` 等分页规则也只有它认。
  代价是无法静默生成文件，因此「打印」与「导出 PDF」合并成同一个动作。
- **hash 约定**：**路由 hash 一律以 `/` 开头**，其余一切（`#某个标题`）都是文档锚点。
  目录跳转与标题锚点都会写 hash，不加区分的话每次点目录都会被当成一次路由跳转。
- **路由**：用 `src/viewer/router.tsx`（约 60 行）替代 react-router。扩展页面只能用 hash 路由，
  而 react-router 全系列版本都带有 SSR/RSC 场景的公开漏洞告警，虽与纯客户端场景无关，
  但会让 `npm audit` 长期不干净。当前 API 与 react-router 心智一致，需要时可平滑换回。

### 性能基线

`npm run bench` 跑管线基准（CPU 部分，不含布局绘制）。
大文档压测样本用 `node scripts/make-fixture.mjs <MB> > 路径.md` 生成。

浏览器实测（同一台机器，拖入文档到首个标题可见）：

| 文档 | 首屏 | 最长单任务 | 渲染 CPU | 备注 |
| --- | --- | --- | --- | --- |
| 1MB  | 655ms → **288ms** | 621ms → **144ms** | 164ms → **152ms** | — |
| 10MB | 19157ms → **239ms** | 19138ms → **528ms** | 7555ms → **1327ms** | 全量落 DOM 仍需约 46s，期间可正常滚动 |

**已知边界**：正文是全量落 DOM 的，10MB 文档产生 33 万节点、约 580MB 堆。
「100MB 不卡死」只在「不冻结、可交互」的意义上成立——真正的 100MB
需要虚拟滚动，而那会牺牲浏览器原生查找、打印与导出的完整性，本阶段没有做。

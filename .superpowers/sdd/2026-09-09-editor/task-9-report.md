## 一、高亮由谁负责，为什么这么选

### 结论

**由本次新增的 `src/search/block-highlight.ts` 自己画**，走 CSS Custom Highlight API，
画在**块 widget 的渲染结果**上，按块建索引，随块的挂载/增强重画。

`@codemirror/search` 在这个项目里**给不出可见的高亮**，`search()` 与
`highlightSelectionMatches()` 都没有加进 extensions——加了是纯粹的死重量。

### 为什么 CodeMirror 那套在这里是不可见的

不是「`highlightSelectionMatches` 只管选区、不管全量命中」这一层的问题（虽然那也是事实），
而是更硬的一条：

`live-preview.ts` 在只读态下把**每一块源码整段**换成了块 widget：

```ts
Decoration.replace({ widget: new BlockWidget(block, cache), block: true }).range(from, to)
```

`replace` 装饰覆盖的文本**不参与渲染**。屏幕上从头到尾没有一个源码字符。
而 `@codemirror/search` 的全部高亮（`highlightSelectionMatches`、以及它自带搜索面板里的
全量命中高亮）都是 `Decoration.mark`——挂在一段根本不渲染的文本上，**一个像素都画不出来**。

所以「不打开 CM 的面板就没有全量高亮」在本项目里甚至不是主要矛盾：**打开面板也一样看不见**。
只能自己画，而且必须画在渲染结果上。

### 为什么仍然是 CSS Custom Highlight API，而不是往命中处插 `<mark>`

块 DOM 由 `block-cache` 按键复用——同一个节点滚出视口再滚回来还是它。往里插标签等于把
用户的搜索痕迹**焊进缓存**，清高亮时还得原样拆回去，一步没拆干净就污染了导出产物
（`export/dom-snapshot.ts` 直接取屏幕上的节点）。Highlight API 只是给浏览器一组 Range，
DOM 一个字节都不改。这一条与旧实现的理由相同，是这次唯一原样保留的设计。

### 与旧 `highlight.ts` 的实质差别（不是重命名）

| | 旧 `search/highlight.ts` | 新 `search/block-highlight.ts` |
| --- | --- | --- |
| 索引范围 | `document.querySelector('.markdown-body')`——**每个块都带这个类名，只取到第一块** | `view.dom.querySelectorAll('.cm-md-block')`，全部挂载中的块 |
| 重画时机 | 只在结果变化时画一次 | 结果变化 + `MutationObserver`（块挂载/卸载、Shiki 上色、Mermaid 出图都会让上一批 Range 指向已被销毁的节点） |
| 「当前命中」的定位 | 全篇一条文本流里的下标 | 「第几块的第几处」（`ActiveSlot`），这是源码坐标与渲染坐标之间唯一稳定的对应 |
| 影子文本 | 只跳过 `svg` | 跳过 `svg` 与 `.katex-mathml`（后者与可见的 `.katex-html` 逐字重复，不跳会把每处公式命中画两遍） |

### 高亮与计数的不对齐（如实记录，实测过）

计数走源文本、高亮走渲染结果，两者在少数查询上对不齐。实测三类：

| 情形 | 计数 | 高亮 | 解释 |
| --- | --- | --- | --- |
| 普通词（`查找目标` / `function`） | 20 / 600 | 与屏幕上肉眼可数的命中**逐项相等**（见第三节对账表） | 对齐 |
| 只匹配语法标记（`**粗体**`） | 1 | 0 | 屏幕上没有 `**` 这两个字符可画。跳转仍然把那一块带到视口里 |
| Mermaid 图里的标签（`alpha`） | 计入 | 不画 | 图内文字在 `svg` 里，被刻意跳过 |

Mermaid 那条是**主动的取舍**，不跳更糟：Mermaid 为量文字宽度会再渲染一份隐藏标签，
一处源码命中会被画成两处、其中一处还看不见；图内文字也没有稳定的「第几处」次序能跟源码对上。
理由写在 `SHADOW_SELECTOR` 上方。

实测（`rich.md`，含 KaTeX 公式 + Mermaid 图 + 表格）：源码 5 处 `alpha`，画出 4 处，
差的正是 Mermaid 那一处；控制台 0 异常。

## 二、`markNavigation` 接线：保住了，而且收窄了

### 保住

`useSearch.ts:189`：

```ts
useDocumentStore.getState().markNavigation();
view.dispatch({ effects: EditorView.scrollIntoView(match.from, { y: 'center' }) });
```

紧挨着滚动那一行、在同一个同步流程里——`scrollIntoView` 的 dispatch 会同步触发视口变化，
`MarkdownEditor` 随即 `enhanceMounted`，那批 Promise 一个微任务后就回调 `onEnhanced`；
指望滚动落定后的 `scroll` 事件撤防一定来不及。这一条与 `TocPanel.handleSelect` 的时序要求
完全一致，注释里写了。

### 三条判定标准逐条对照

| 判定 | 新实现如何满足 |
| --- | --- |
| 1. 起因是用户的一次明确操作 | 只在 `current` 变化时触发，而 `current` 只由「用户输入查询词」和「按上一处/下一处」改变。页面自己的时序（块渲染、增强、自动刷新）不会改它 |
| 2. 它真的把视口带到别处 | **这次收窄了**：先算出当前命中在渲染结果里的 Range，只有它没有完整落在滚动容器可视区内才滚、才记。目标已经在屏幕上就直接 return，一次导航都不记 |
| 3. 落点是我们自己算出来的 | `EditorView.scrollIntoView(match.from)`，落点由源码偏移算出，`useReadingPosition` 的值比对认不出这段位移 |

第 2 条的判据有个坑值得写下来：**不能用 `view.scrollDOM` 量可视区**。本项目的
`.cm-scroller` 被显式设成 `overflow: visible`（`editor/theme.ts`：编辑器随内容自然增高，
真正滚动的是 AppShell 的 `<main>`），CodeMirror 的 `scrollDOM` 仍旧指着 `.cm-scroller`，
拿它量会得到「整篇文档都在视口里」，于是永远判成「已经看得见」，**跳转一次也不会发生**。
`viewportBounds()` 因此沿着祖先找第一个真正会滚的元素，注释里写明了。

### 如何验证保住了

三条独立证据：

1. **单测**（撤销后失败）：`跳到命中处时记一次显式导航`、`按下一处再记一次导航`；
   反向对照 `命中已经在视口里时不记导航`。
2. **浏览器对照实验**：撤销这一行重新 `npm run build`，7 格延迟**全部**复现缺陷（第三节判据 4）。
3. **浏览器正向实验**：修复后 7 格延迟全部落在命中处，连采 6 秒不动。

## 四、源文本搜索的行为变化

改成搜源文本之后，能搜到的东西变了。如实列出，注释写在 `matcher.ts` 的 `countMatches` 上：

**多出来的（好事）**：源码里有什么就能搜到什么。搜「粗体」能命中 `**粗体**`（实测 1/1），
搜 `](` 能命中链接语法，搜代码块的围栏语言标记也可以。

**少掉的（代价）**：一段被行内标记切断的连续文字会落空。屏幕上显示「这是粗体字」，
源码是 `这是**粗体**字`，搜「是粗体」**搜不到**（实测「无匹配」）。旧的 DOM 实现能搜到。

不为它做「源码偏移 → 渲染偏移」的映射：那需要为每个行内标记维护一张字符级偏移对照表，
而 markdown-it 的 token 只带**行号**、不带行内字符偏移，做不到而且脆弱。这是所有源码型
编辑器的一致行为，且随着实时预览，用户看到的和搜到的本就是同一份文本。

附带的两处小行为变化，也写进注释了：

- `literal: true`。CodeMirror 的 `SearchQuery` 默认会把查询词里的 `\n`、`\t`、`\\` 当转义
  序列解释，一个纯文本查找框不该这样——输入 `\n` 应该找 `\n` 这两个字符。用例锁住了。
- 大小写折叠交给 `SearchCursor` 按 Unicode 规则做，不再自己 `toLowerCase()`。
  `İ`、`ß` 这类字符 `toLowerCase()` 会**改变长度**，自己折叠会把偏移量算错。

## 六、遇到的问题与取舍

### 1. `SearchBar` 原先在 `EditorViewProvider` 之外——不挪的话整个功能是哑的

`App.tsx` 里 `<SearchBar />` 是 `<EditorViewProvider>` 的**兄弟**。改用 `useEditorView()`
之后它会永远拿到 `null`，查找**静默**什么都不做：查找条照常弹出、输入框照常回显、
计数永远空白。这正是「测试全绿而功能是坏的」的标准配方。已把 `<SearchBar />` 移进
provider 内（仍在 `AppShell` 之外，因为它是全局浮层）。注释写在 `useSearch` 的 `view` 上方。

### 2. `react-hooks/set-state-in-effect` 挡住了「effect 里同步 setState」

新 lint 规则不允许在 effect 体里同步 `setState`。搜索这件事的形状本来就是
「向外部系统问一个答案，拿到了再写回 React」，所以让一次主线程（`yieldToMain()`，
项目已有的工具）之后再写回——顺带保住了「输入框回显不等整篇扫完」这个体验。
如实说明：这里让步**不是**必须的性能手段，`SearchCursor` 只是一次线性字符串扫描，
与旧实现遍历几十万个文本节点不是一个量级。

### 3. 没有加 `search({ top: true })` 与 `highlightSelectionMatches()`

简报 Step 4 要求加，本次**没有加**，理由在第一节：它们产出的都是 `Decoration.mark`，
在块 widget 之下完全不可见，加进去是死重量，还会让后来人以为「高亮是 CodeMirror 管的」。
`SearchQuery.getCursor(state)` 不需要 `search()` 扩展就能用，所以功能上也不缺什么。
`MarkdownEditor.tsx` 因此一个字没改。

### 4. 简报要求「删掉 `highlight.ts`」，但高亮不能没人管

按第一节的分析，删掉旧文件的同时新建了 `block-highlight.ts`。它不是重命名：
索引范围、重画时机、当前命中的定位方式三处都变了（见第一节的对照表）。
被原样保留的只有「用 Highlight API 而不是插 `<mark>`」这一条设计与它的理由。

### 5. 「当前命中」在渲染侧的定位用「第几块的第几处」

块 widget 里的 DOM 与源码之间没有字符级对应（语法标记被吃掉、实体被解码、
锚点链接是凭空多出来的）。`ActiveSlot = { blockKey, ordinal }` 是两套坐标之间唯一稳定的
对应关系。它在「一块里的源码命中数 ≠ 渲染命中数」时会错位（例如一块里同时有
`**粗体**` 和普通的「粗体」），此时当前命中层可能画在同块的另一处，或者干脆不画
（`ranges[ordinal] ?? null`）——不会抛错、不会画到别的块上。实测未构造出这种文档，
写在这里备查。

## 七、遗留与不确定

1. **Mermaid 图内文字被计数但不高亮**（第一节末）。这是取舍不是疏漏，
   但如果将来有人报「图里的字搜到了却没高亮」，答案在 `SHADOW_SELECTOR` 的注释里。
2. **`file://` 场景未验证**。全部实测跑在 `http://127.0.0.1` 上，与 task-8c/8d 的边界相同。
3. **真实 `chrome.storage` 未参与**，用的是 localStorage 替身；被替身的还有「内容脚本宿主」
   这一处，同 task-8c/8d。
4. **编辑态未验证**。当前 `ReaderPage` 固定 `readOnly`，编辑态下光标所在的块会变回源码，
   那一块里的命中会同时存在于「源码文本」（不渲染高亮）与「块 DOM」（已经不存在）两侧，
   高亮会在那一块上缺失。等编辑态真正接上时需要再看一次。
5. **超大文档未压测**。`DEFAULT_MATCH_LIMIT = 5000` 原样保留，`truncated` 仍会在计数后
   加 `+`，但没有在 10MB 文档上实测过重画的开销（每次重画要对挂载中的每一块重建文本索引，
   量级是「一屏的块数」，实测 6~8 块）。

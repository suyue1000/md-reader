## 缺陷一（Critical）：源码相同的重复块互相抢 DOM 节点

### 根因

`block-cache.ts` 的 `acquire(key, html)` 对同一个键返回**同一个 DOM 节点**，而
`block-render.ts` 直接拿块的源码文本当键。一个 DOM 节点在文档树里只能存在于一个
位置——第二个 widget 挂上它，就把它从第一处摘走了。

### 设计选择：把键从「内容」改成「内容 + 出现序号」

键改成 `` `${序号} ${源码文本}` ``，序号是「同样的源码文本在本篇文档里第几次出现」。

**为什么选它，而不是另外两条路：**

| 方案 | 代价 |
| --- | --- |
| **内容 + 出现序号**（采用） | 只动 `renderBlocks` 里造键的那几行。缓存的价值一点没丢：滚出视口再滚回来，键不变、节点不变、`isEnhanced` 不变，Shiki 与 Mermaid 都不重跑。唯一的成本是重复块之间不再共享增强结果——两段一模一样的代码各上一次色。这个成本是**必须付的**：它们本来就得是两个节点。 |
| 缓存存模板、`acquire` 返回克隆 | 增强是就地改**活节点**的（Mermaid 把 SVG 插进去、Shiki 换掉 innerHTML），克隆源永远停在未增强的样子，等于把缓存的全部价值扔掉；Mermaid 的 SVG 还带 id，克隆会撞 id。 |
| widget 自己持有节点、缓存只存增强结果 | 要把「增强结果」从 DOM 里剥出来重新序列化，等于推翻「缓存节点本身」这个设计前提，改动面远超一个缺陷该有的规模。 |

**序号加在前面而不是后面**：序号只含数字，键因此能按第一个空格唯一地分回
(序号, 文本)，两个不同的块不可能算出同一个键。加在后面就没有这条保证——源码文本
自己也可能以「空格 + 数字」结尾。

**序号按「相同文本的第几次出现」而不是「块下标」**：按下标的话，在开头插一段就会
让后面每一块的键全变，整篇缓存作废、Shiki 与 Mermaid 全部重跑。按出现次数计数，
唯一块的键与位置无关，受影响的只有重复块本身。

同一轮里对齐的三处：`acquire` 写进 `node.dataset.blockKey` 的值、`MarkdownEditor`
的 `enhanceMounted` 靠它认块、`BlockWidget.eq()` 靠它决定复不复用 widget——三处读的
都是同一个 `RenderedBlock.key`，改键自动一致。`trailing` 块（脚注汇总）顺带从
「块列表下标」改成「trailing 计数」，同样是为了插入内容时不失效。

`block-cache.ts` 的文件注释新增一段「对键的要求」，把这条不变量写在缓存自己身上，
并说明为什么缓存**不**做「返回克隆」之类的自保。

### 实测（`dup.md`：20 章，每章正文与代码块全篇一字不差，外加两个同名 `## 重复标题`）

## 缺陷二（Important）：同一会话内用相同内容重开同一文档，目录永久变空

### 根因

`setDocument` 会清空 `toc`，等着 `MarkdownEditor` 在下一轮块渲染里通过 `onHeadings`
重新填上。但重建编辑器的 effect 只依赖 `[documentId, markdownSettings]`——重开同一篇
文档时 documentId 没变；内容也没变，于是灌内容的那个 effect（`doc.toString() === value`
就 return）也不 dispatch。两条路都不走，`onHeadings` 再也不被调用，目录就空在那里。

连锁后果：`usePendingAnchor` 的「`toc.length === 0` 就什么都不做」门槛让锚点永远兑现
不了，`pendingAnchor` 滞留非 null，而 `useReadingPosition` 的两条恢复路径都看
`pendingAnchor !== null`——于是这一次打开的阅读位置恢复也被一并挡掉。

### 修法

`document.store` 里已经有现成的判据：`openEpoch`（每次 `setDocument` / `reset` 自增，
`applyRefreshedDocument` 不自增）。给 `MarkdownEditor` 加一个可选的 `openEpoch` prop
并列进重建依赖，由 `ReaderPage` 从 store 传下来。

- 换文档：documentId 与 openEpoch 同时变，同一轮只重建一次。
- 重开同一篇：openEpoch 变 → 重建 → `rerender` → `onHeadings` → 目录回来、锚点被消费。
- 自动刷新：openEpoch **不**变 → 不重建，仍旧走 dispatch，撤销栈、滚动位置与块缓存都保住。

这与 `useReadingPosition` 的闩锁、`usePendingAnchor` 的撤防用的是同一个判据，
「documentId 标识文档、openEpoch 标识一次打开」这条区分在整个模块里保持一致。

### 实测（`uniq.md`，同一会话内让宿主用**完全相同的内容**再发一次 `md-reader:load`，并带 `#第-9-章`）

| | 撤销 openEpoch 的对照 | 修复后 |
| --- | --- | --- |
| 首次打开的目录项 | 21 | 21 |
| 重开后的目录项 | **0** | 21 |
| 侧栏是否显示「这篇文档没有标题」 | **是** | 否 |
| 锚点是否被消费 | **否**，scrollTop 恒为 0 | 是，落在「第 9 章」，标题距容器顶 **7px** |
| 重开后的 scrollTop | 0 | 6226 |

再不带锚点重开第三次：目录仍为 21，阅读位置恢复正常（实测 5884 → 5890，残差来自
增强后总高的变化）。

### 回归测试（撤销后失败的用例）

撤销 `src/editor/MarkdownEditor.tsx` 到 HEAD 后：**1 例失败**
- `MarkdownEditor.test.tsx > 用完全相同的内容重开同一篇文档时，重新送一份目录出来`

另加一例锁住另一半不变量（撤销时不会失败，但防止将来「顺手」把自动刷新也改成重建）：
`只是内容变了（自动刷新）不重建编辑器`。

## 缺陷三（Important）：`block-height.ts` 的常量推导是错的

### 核对结果：错得比简报说的更多，而且**值本身也该改**

简报点名了两处（`CHARS_PER_LINE` 的版心、`HEADING_PX` 的 em 基准）。逐条核对 CSS 并
在真实构建里量过之后，发现原来的推导有两条**根本性**的错：

**1. markdown.css 里的块间距根本没生效。** Tailwind 的 Preflight 把 p / ul /
blockquote / h1–h6 的 margin 全部归零，而 `.markdown-body p { margin: 0 0 1em }` 位于
更低优先级的 layer 里。实测块内首元素的 computed `margin-bottom` 是 `0px`。
`BLOCK_GAP_PX = 16`「= `margin: 0 0 1em`」这条推导指向的 CSS 属性**根本不参与布局**。
块与块的间隔其实来自两块之间那个**空行**——它是编辑器里一条真实的行，由 CodeMirror
自己按 27.2px 记进高度图，不归这个函数管。

**2. `.cm-content` 的 `white-space: break-spaces` 会继承进块 widget。** 于是净化后
HTML 里每一个「块级标签后紧跟的换行」（markdown-it 的块级渲染器几乎每个都以它收尾）
都被保留成一次真实换行，各占一个 27.2px 的空行盒。一个 `<p>甲</p>\n` 因此有
27.2 + 27.2 = 54.4 的正文高度，而不是 27.2。原来的模型里**完全没有这一项**。

加上 CodeMirror 给块 widget 的上下内边距（实测 computed `padding: 6.4px 0`，本项目
没写过这条），每块的固定开销是 12.8 + 27.2 ≈ **40**，不是 16。

### 常量的新值与依据（全部在真实构建里量过）

| 常量 | 旧 | 新 | 依据 |
| --- | --- | --- | --- |
| `TEXT_LINE_PX` | 27 | 27 | 16px × 1.7 = 27.2，实测一致 |
| `BLOCK_GAP_PX` | 16 | **删除**，换成 `WIDGET_PADDING_PX = 13` + `BLOCK_CHROME_PX = 40` | 13 = 实测 `padding: 6.4px 0`；40 = 13 + 一个空行盒 27 |
| `CHARS_PER_LINE` | 86 | **110** | 版心 980 − `.cm-content` 左右各 32 = 916px；16px 下一个半宽单位 8px → 理论 114。实测中文行盒顶到 912px（114 单位），西文按词折行只用到 883px（110 单位），取小的那个偏保守 |
| `CODE_LINE_PX` | 22 | 22 | 0.85em(13.6px) × 1.6 = 21.76，实测一致 |
| `CODE_CHROME_PX` | 51 | **72** | 实测：bar 34.1 + pre 上下内边距 23.1 + 上下边框 2 + widget 内边距 12.8 = 72.0。代码块的 HTML 以 `</figure>` 收尾、后面不带换行，所以这一支**不再**叠加块外壳 |
| `TABLE_ROW_PX` | 40 | **60** | `<tr>` 实测 40.7；`.markdown-body table` 是 `display: block`，HTML 里的换行一部分落在表内匿名盒被丢弃、一部分没有，按实测的 4 行表整块 280px 反推每行 60 |
| `IMAGE_PX` | 320 | 320 | 经验值，不变（真实高度要等文件加载完才知道） |
| `DIAGRAM_PX` | 320 | 320 | 经验值，不变。实测一张两节点的最小流程图整块 208.8px，真实文档里的图普遍更高 |
| `HEADING_PX` | [58,50,35,31,29,28] | **[88,78,65,62,60,59]** | 实测 88.3 / 78.1 / 64.9 / 61.8 / 59.7 / 58.7。算式：行盒（1.85em×16×1.3 = 38.5 等）+ h1/h2 的 0.3em 下内边距与 1px 下边框 + 外壳 40。em 基准是标题自己的字号 |

行为上还改了两处分支：

- **缩进式代码块**不再按 `CODE_LINE_PX` 算。它只是一个裸 `<pre>`，markdown.css 没给它
  改字号，实测 pre 与内部 code 都是 16px / 27.2px 的正文行高（4 行的块实测 148.7，
  按正文行高算得 148，按代码行高算只有 128）。
- **兜底分支**（段落 / 列表 / 引用块 / 定义列表）加上空行盒计数
  `countOccurrences(html, '>\n')`。只数**标签后面**的换行，段落内部的软换行不算——
  那是真实的文字行，已经由源码行数算过一次，重复计会把两行的段落估成四行。
  这一项不是微调：一个三项列表有 5 个这样的换行（`<ul>` 后、每个 `</li>` 后、
  `</ul>` 后），合计 136px，不数的话整块被低估将近一半。

## 缺陷四（Important）：documentId 含 hash 导致阅读位置记录分裂

### 根因与修法

`useEmbeddedDocument` 用 `message.url`（宿主的 `location.href`）当 documentId，
而缺陷「跳转后同步地址栏」修好之后，点一次目录宿主地址栏就带上 `#章节`，刷新即是
另一条阅读位置记录。

新增 `stripHash(url)`，`id` / `path` / `baseUrl` 三处一并用剥过 hash 的地址：
`path` 是状态栏显示用的，带个 `#章节` 只是噪音；`baseUrl` 在解析相对地址时本来就会
忽略 base 的片段，剥掉不改变任何结果。用字符串截断而不是 `new URL`——`file://` 这类
地址在个别环境下构造 URL 会抛，而 hash 一定从第一个 `#` 开始、查询串里不可能出现 `#`。

hash 的**功能**一点没动：`message.hash` 照常喂给 `setPendingAnchor`。

### 用例（3 条，撤销后失败 1 条）

在 `useEmbeddedDocument.test.ts` 里补了一组走**真实 hook**的用例（伪装 `window.parent`
+ `?embed=1` + 匹配的 `event.source`，三条缺一这个 hook 就整个不干活、用例会以
「什么都没发生」的形式假通过）：

- `documentId 不含 hash：点过目录再刷新仍是同一条阅读位置记录`
- `剥掉的只是 hash 对身份的影响，锚点照样被存下来待跳转`
- `本来就没有 hash 的地址原样作为 id`

把 `stripHash(message.url)` 改回 `message.url` 后，第一条失败。

### 已知影响

存储里既有的、键上带 hash 的阅读位置记录会成为孤儿，由 `prune()` 的 `MAX_ENTRIES`
自然淘汰。没有做迁移：迁移需要知道「哪些带 hash 的键属于同一篇文档」，而合并之后
选哪一条位置又是新的取舍，代价大于收益。

## 缺陷五（Minor）：TocPanel 的注释名不副实

**选择改注释，不改代码。** 理由写进了注释本身：

1. 「跳成了」这个判据本身有二义性——目标本来就在当前位置时，不动才是对的；
2. 要确认就得等滚动落定（`afterScrollSettles`），地址栏因此晚一百多毫秒才更新，
   而用户此刻正盯着它；
3. 紧接着那行高亮是**无条件**写的，另外两条跳转路径（地址栏锚点、正文 `#锚点` 链接）
   也都无条件写地址栏。只给这一条加前提，三处就对不齐了。

审查者观察到的「scrollTop 恒为 0 而地址栏照写」，成因是定位机制本身的缺陷（估算高度、
块身份），要在那里修——本次缺陷一修的正是其中一条。让目录面板用「那我不写地址栏了」
来掩盖，等于把一个静默失效换成另一个静默失效。

## 实测中发现的、**本次没有修**的既有缺陷

### A（Important，pre/post 两个构建都复现）：阅读位置恢复之后的第一次目录跳转会被吞掉

**复现**（最普通的用户路径，与本次五个缺陷无关）：读一篇文档滚到中段 → 刷新页面 →
阅读位置恢复 → 点目录里一个远处的章节。**第一次点击 scrollTop 一动不动，第二次才生效。**

实测（`uniq.md`，连跑 3 次，HEAD 与修复后完全一致）：

| | HEAD | 修复后 |
| --- | --- | --- |
| 刷新后恢复到 | 5881 | 5881 |
| 点「第 18 章」 | 5885（**没跳**） | 5885（**没跳**） |
| 再点一次 | 12215 ✅ | 12215 ✅ |

**机制已定位**：`useReadingPosition` 的 `onEnhanced` 校正。目录点击引起视口变化 →
`enhanceMounted` → `onEnhanced` → 校正把用户拽回记录里的位置。第二次点击之所以能成，
是因为第一次点击的 `scroll` 事件已经把 `userScrolledRef` 置位、校正随之撤防。

**佐证**：在点目录**之前**先做一次 60px 的用户滚动（把 `userScrolledRef` 置位），
第一次点击就正常了——HEAD 与修复后各跑一次，都是 5941 → 12211。

没有在本次一并修：它要动的是 8c 刚建立起来的那套「闩锁 + 撤防」判据，需要单独设计
（比如让程序化跳转显式通知 `useReadingPosition` 放弃本轮校正），不该顺手改。

### B（Minor）：每个块都白白多出一个 27px 的空行盒

即缺陷三根因里的第 2 条。`.cm-content` 的 `white-space: break-spaces` 继承进块 widget，
让净化后 HTML 末尾的换行占掉一整行。一篇 60 块的文档约 1600px 的死白。
给 `.cm-md-block` 补一句 `white-space: normal` 就能消掉，但那是一次会改变全篇排版的
改动，不该由「修估算注释」顺手带出来。已写进 `block-height.ts` 的文件注释。
注意：真去改的话，`block-height.ts` 的常量要跟着回到「不含空行盒」的一套。

1. **差点把一个 NUL 字节提交进源码。** 造键时最初用了 `\0` 当分隔符，`git diff` 把
   `block-render.ts` 报成 `Bin 2708 -> 4833 bytes`（二进制文件）才发现。改成空格：
   序号只含数字，按第一个空格分界同样是单射的，而且可读、可调试。
2. **实测一度用了没重新构建的 dist**，导致「修复后」与「对照组」跑出完全一样的结果。
   排查后重建才拿到正确对照。凡是切换 `dist` 的实测，之后都显式重新 `npm run build`。
3. **块高度的真相与 CSS 对不上。** 一开始按 markdown.css 的算式重推，得到的 h1 是 66，
   而浏览器量出来是 88.3。硬对了几轮才发现是 Preflight 归零 + `break-spaces` 两条，
   两条都不在 CSS 文件里写着。这也是为什么新注释把**实测值**和算式并排列出来——
   只写算式的话，下一个人会重蹈同一条覆辙。
4. **缺陷一在浏览器里的对照组一开始不明显**：`duplicateKeysMounted` 恒为 0，因为
   一个节点本来就不可能同时出现在两处。改用「同时挂在 DOM 上的、内容相同的段落有几个」
   做判据，对照组 1 个 vs 修复后 4 个，才把症状测清楚。

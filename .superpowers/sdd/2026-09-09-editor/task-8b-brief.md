## 缺口一：正文里的 `#锚点` 链接是坏的

**现状**：`useRelativeLinks` 明确把 `href.startsWith('#')` 的链接交给浏览器原生处理。在虚拟化之前这没问题——所有标题都在 DOM 里，浏览器自己就能跳。现在编辑器只渲染视口附近的块，视口外的标题根本不在 DOM 里，浏览器找不到目标，点击毫无反应。

这类链接在 Markdown 文档里极常见：手写的目录、「见下文的 xxx 一节」这类交叉引用，全都是 `[文字](#标题锚点)`。

**要求**：拦截这类链接，走与 `usePendingAnchor` 相同的机制——按锚点 id 在 store 的 `toc` 里找到对应行号，再调 `scrollToLine`。

注意 `toc` 是树形结构（`TocNode` 有 `children`），按 id 查找需要遍历整棵树。Task 8 里已经有同样的查找逻辑，**不要写第二份**——抽出来共用，或者复用已有的那份。留两份「按 id 找行号」的实现，迟早会分岔。

找不到对应锚点时的行为要明确：不要静默失败，也不要跳到文档顶部。保持原地不动是可接受的（用户至少知道没跳成），但要在注释里写明这是有意选择。

## 缺口二：锚点落点比目录点击短约 8px

**现状**（Task 8 实现者的实测对照，同一文档同一目标）：

| 路径 | scrollTop | 标题距容器顶 | 侧栏高亮 |
| --- | --- | --- | --- |
| 地址栏锚点 | 5191 | 10.4px | 第 10 章（错） |
| 目录点击 | 5199 | 6.8px | 第 11 章（对） |

**成因**：锚点跳转发生在 Shiki 上色完成**之前**，上方内容随后变高，落点因此偏浅。阅读位置恢复有 `onEnhanced` 做增强后校正，而锚点这条路径没有。

用户小幅滚动不会自愈——侧栏高亮忠实反映了视口的真实位置，是落点本身短了。

**要求**：给锚点跳转补一次增强完成后的校正。

**这里有个必须小心的交互**：Task 8 刚刚加了一道闩锁（`anchorDocRef`），作用是「带锚点打开时，阅读位置的恢复与 `onEnhanced` 校正都不执行」，防止锚点被阅读位置覆盖。你要加的校正**必须只把锚点补到位，绝不能顺手把阅读位置恢复回来**——那正是闩锁要挡住的事。

换句话说：`onEnhanced` 之后要发生的是「重新按锚点行号滚一次」，不是「执行 applyPosition」。

去读 `src/hooks/useReadingPosition.ts` 里闩锁那段的注释，理解它为什么存在，再动手。

## 验收判据（硬要求）

`npm run verify` 通过**不等于**这两个缺口修好了。这个项目已经吃过两次这个亏。

必须实际验证：
1. 打开一份正文里带 `[文字](#某标题)` 链接、且目标标题在视口之外的文档，点击该链接，确认跳到目标位置。
2. 带 `#锚点` 打开一份含 Shiki 代码块或 Mermaid 图的文档，确认增强完成后落点被校正、侧栏高亮指向**正确的那一章**（对照上表，应与目录点击的结果一致）。
3. 确认闩锁仍然生效：打开一篇**之前读过、存有阅读位置**的文档并带锚点，落点应是锚点而不是上次读到的位置。这条是回归验证，别把 Task 8 刚修好的东西弄坏。

`fixtures/` 目录里有可用的样例文档。如果能用 headless Chrome 之类的方式实测（不引入新依赖、不联网），把观察到的具体数字写进报告；确实做不到就明确说明验到哪一步、哪一步没验到，**不要含糊地说「应该可以了」**。

# Task 8b 报告：锚点导航收尾（正文 `#锚点` 链接 + 增强后落点校正）

## 一、做了什么

### 1. 抽出共用的「按 id 找行号」

`src/markdown/toc.ts` 新增：

```ts
export function findHeadingLine(nodes: readonly TocNode[], id: string): number | null
```

内部就是 `flattenToc(nodes).find(n => n.id === id)?.line ?? null`，即 Task 8 已经写在
`usePendingAnchor` 里的那一份，原地抽出来共用，**没有写第二份实现**。两个调用方：
`usePendingAnchor`（地址栏锚点）与 `useRelativeLinks`（正文里的 `#` 链接）。

返回 `null` 而不是 `-1`/`0`：行号 0（文档第一行）本身是合法跳转目标，用 0 表示
「没找到」会让「跳到开篇」和「跳不动」变成同一件事。注释里写了这一条。

### 2. 缺口一：正文里的 `#锚点` 链接（`src/hooks/useRelativeLinks.ts`）

原来 `href.startsWith('#')` 直接 return 交给浏览器。改成四段判定，顺序即优先级：

1. `findHeadingLine` 命中 → `preventDefault` + `scrollToLine`（与目录点击、地址栏锚点
   走的是同一条路径，落点因此一致）；
2. 命中但编辑器未就绪（`view` 为 null）→ **放行**，不吞掉这次点击；
3. 不是标题、但目标就在 DOM 里（脚注引用 `#fn1`、手写 `<a id>`）→ **放行**给浏览器。
   这条路径在虚拟化之前就是好的，抢过来反而要重新实现一遍「元素滚进视口」；
4. 都不是 → `preventDefault` + **原地不动** + `log.warn`。

第 4 条是简报要求「行为要明确」的那一条，代码注释里写了为什么另外两种行为更差：
放行会让浏览器把地址栏 hash 改成一个跳不到的片段（页面不动、后退键行为变得莫名其妙，
**这一点在浏览器里实测复现过**，见第四节 HEAD 基线），而「兜底跳文档顶部」会把用户从
正在读的地方一把甩走——一次误跳比没跳难恢复得多。

两个连带改动：

- **hook 现在接收 `view`**：`useRelativeLinks(view)`，与 `useScrollSpy(view)` /
  `usePendingAnchor(view)` 一致。
- **「打开过文件夹」这道门槛从 effect 顶端挪进了相对路径分支**。原来
  `if (!container || rootName === null || currentPath === '') return;` 是整个监听器的前提，
  留在那儿的话「没打开文件夹、只单独打开一个 .md」时连锚点都跳不了——而那是最常见的用法。
  锚点分支不需要工作区，相对路径分支需要。有回归测试锁住这条。

  百分号解码是必须的，不是防御性代码：markdown-it 渲染出来的 href 是
  `#%E7%AC%AC-11-%E7%AB%A0`，而目录里的 id 是 `第-11-章`。不解码的话**所有中文标题的锚点
  链接全部失效**——这条在浏览器里直接看到了（见第四节）。`useEmbeddedDocument` 处理地址栏
  锚点时做的是同一步。解码失败（半截转义）退回原文，不让一个坏链接打掉整个点击处理。

- 目录与 view 走 ref（在 effect 里同步）而不是 effect 依赖：每渲染一轮块就是一棵新目录树，
  编辑期每 200ms 一次，放进依赖会让这个纯事件委托的监听器被反复拆装。这也是上一轮审查
  对 `useScrollSpy` 依赖 `flat` 提的那条 Minor，不想在新代码里重犯。

### 3. 缺口二：增强完成后的落点校正（`src/hooks/usePendingAnchor.ts`）

`usePendingAnchor(view)` 现在返回 `{ onEnhanced }`，`ReaderPage` 把它与
`useReadingPosition` 的 `onEnhanced` 合并成一个 `handleEnhanced` 交给 `MarkdownEditor`。

三个 ref：

- `anchorLineRef`：本篇文档的锚点落在哪一行。**必须自己记**——`pendingAnchor` 是消费一次
  即清空的，等到 `onEnhanced` 触发时现读一定是 null。这与闩锁存在的理由是同一个。
- `expectedScrollTopRef`：我们自己每次滚动落定后的 `scrollTop`，在 rAF 里量（CodeMirror 的
  滚动发生在下一帧的测量阶段，当场读到的是滚动前的值）。
- `measureFrameRef`：卸载时取消那个 rAF。

`onEnhanced` 的逻辑：拿不到行号就什么都不做；`container.scrollTop` 与期望值差出
`ANCHOR_SCROLL_TOLERANCE_PX = 2` 就认定用户自己滚走了，**撤防并且不再恢复**；否则
`scrollToAnchor(view, line)` 重滚一次。换文档时（`documentId` 变）撤防，effect 声明在消费
effect 之前，保证同一轮提交里先撤防后置位。

**用户滚走的撤防不是加固，是必需的**：`onEnhanced` 在每次视口变化之后都会触发（见
`MarkdownEditor` 里 `enhanceMounted` 的调用点），而用户滚动本身就会改变视口。不撤防的话
用户每滚一下都被弹回锚点，文档等于滚不动了。

2px 这个容差为什么够，有实测依据：Task 8 的采样表里，带锚点打开后 Shiki 从未上色到全部
上色的 6 秒里 `scrollTop` 恒为 5191 ——增强造成的漂移发生在**文档坐标**里（上方内容变高、
目标行整体下移），不体现为 `scrollTop` 变化。本轮自己的逐帧采样再次确认了这一点（见第四节
缺口二的表：漂移 462px 期间 `scrollTop` 一动没动）。

### 4. 闩锁：一个字都没改

`src/hooks/useReadingPosition.ts` **未修改**（`git diff` 里没有这个文件）。校正做的是
「重新按锚点行号 `scrollToLine`」，既不读也不写阅读位置，`anchorDocRef` 因此完全不受影响。
`ReaderPage` 里合并两个 `onEnhanced` 时把锚点排在后面，注释写明理由：万一将来哪次改动让
闩锁漏了一次，后跑的锚点校正还能把落点纠回来，而不是反过来。

## 三、实测中撞上的 HEAD 既有缺陷（不是本次改动引入，未修）

**现象**：文档里只要有 fenced 代码块（```ts 之类，会被 Shiki 上色），`scrollToLine` 对
**尚未渲染进 DOM 的目标**就完全失效——`scrollTop` 一个像素都不动。

**这不是我改坏的**，用 `git stash` 把本次改动全部撤掉后在 HEAD 上复现：

| 文档形态 | 目标 | 点击前在 DOM | HEAD 上的落点 |
|---|---|---|---|
| 13 章，每章一个 ts 代码块 | 第 1 章 | 是 | 1083 ✅ |
| 同上 | 第 2 / 3 / 5 / 11 章 | 否 | **0（全部没动）** ❌ |
| 13 章纯段落（无代码块） | 第 3 章 | 否 | 1876，距顶 5.9px ✅ |
| 同上 | 第 8 章 | 否 | 5645，距顶 6.5px ✅ |
| 同上 | 第 13 章 | 否 | 9415，距顶 6.0px ✅ |

即：**侧栏目录点击（Task 8 的「坏功能 2」）在带代码块的长文档上目前仍然是坏的**，我的
锚点跳转因为走同一个 `scrollToLine`，在这类文档上同样跳不动。

**诊断到的位置**（没有继续深挖修复，超出本任务范围）：`EditorView.scrollIntoView` 派发后，
CodeMirror 确实把视口扩到了目标（`viewport` 从 `0..293` 变成 `7471..10215`），但在这一轮
measure 里 `coordsAtPos(目标)` 返回 `null`，视口随即又缩回 `0..293`，`scrollTop` 始终为 0。
控制台里 CodeMirror 自己打出 `Viewport failed to stabilize`。根因看起来是块 widget 的高度
估算：`BlockWidget` 没有实现 `estimatedHeight`，一个 8 行源码的代码块渲染后可能有几百像素，
CodeMirror 按行数估的高度与真实高度差得太远，滚动目标在几轮 measure 里来回震荡直到放弃。

**为什么 Task 8 没看到**：它的合成文档是纯标题+段落（27 项全部通过），真实 fixture
`sample.md` 只有 17 个标题、整篇较短，代码块之外的目标基本都在首屏渲染范围内。

**建议**：单开一项，方向是给 `BlockWidget` 实现 `estimatedHeight`（用块缓存里上次测到的
高度，没有时按内容类型给一个粗估）。这条如果不修，「目录点击跳转」这个 Task 8 报告为
「已修复」的功能，在最常见的技术文档（带代码块）上其实仍然不可用。

## 四、另一个发现：闩锁是「粘」的（Task 8 的既有行为，未修）

`anchorDocRef` 存的是 documentId 且**从不清除**，而 `ReaderPage` 在整个会话里不卸载。
于是：同一篇文档先带锚点打开、之后再**不带锚点**打开，闩锁仍然认得这个 documentId，
阅读位置恢复被继续挡住。

实测：`crit3-doc` 带 `#第-8-章` 打开一次（存档位置随之更新到 `line 156`）→ 切走 →
不带锚点重新打开 → `scrollTop` 停在 **0**，没有恢复到 line 156。
对照：从未带过锚点的 `crit3-plain` 同样时序，正常恢复（见判据 3 的正向对照）。

**没有动它**，两个理由：一是它属于 Task 8 的闩锁设计，简报明确要求「绝不能因为要加校正就
放宽或绕过闩锁」，改它正是放宽；二是影响有限（只在同一会话内、同一文档、先带锚点后不带
锚点这一条路径上，表现为「少恢复了一次」，不会误跳）。

如果要修，方向是把闩锁从「文档级」收紧成「这一次打开」——比如在恢复 effect 里区分
「`documentId` 没变但 `document` 对象换了新实例」，或者由 `setDocument` 显式复位。
**不建议顺手改**：这道闩锁挡的是一个隐蔽缺陷，任何收紧都需要重跑 Task 8 那 5 个回归用例
外加浏览器实测。

## 六、一处有意为之的行为变化，请审查者留意

**正文里点标题锚点，不再更新地址栏 hash。**

`useEmbeddedDocument` 里有一段 `onHashChange` → `postToHost`，注释写的是
「阅读器内跳转标题后，把锚点回传给宿主，让地址栏与页面保持一致」。它依赖的是**浏览器原生
锚点跳转会改 `location.hash`**。我 `preventDefault` 之后这条不再触发。

没有补回来，三个理由：

1. **它在 Task 8 之后就已经基本失效了**：侧栏目录点击早就改成了 `scrollToLine`，同样不改
   hash。现在只剩「正文里点一个恰好在 DOM 里的标题链接」这一条窄路径还能触发它。
   我的改动让这条窄路径也归到统一机制上，是把不一致收敛掉，不是新增不一致。
2. **补回来有实打实的风险**：`location.hash = x` 在目标元素存在时会触发浏览器自己的片段
   导航，和我们刚算好的落点打架（原生对齐的是标题元素顶边，我们对齐的是块顶边），很可能
   把 Task 8 好不容易调准的 6px 落点又弄歪；用 `replaceState` 则不会派发 `hashchange`，
   宿主根本收不到。
3. 真要做，正确的做法是让**所有**跳转路径（目录点击 / 正文锚点 / 地址栏锚点）统一在
   `scrollToLine` 之后回传一次 hash，那是一项独立的改动，不该塞进本任务。

**建议单开一项**：「跳转后同步地址栏 hash」，范围覆盖三条路径。

## 七、遗留与顾虑

   File System Access 工作区，Playwright 里构造不出来。这条路径我没有改动它的判定逻辑，
   只改了那道门槛的位置，风险我判断是低的，但如实记下没有实测。

# Task 8e 报告：恢复阅读位置之后，第一次目录跳转被吞掉

对象分支 `feat/editor`，基线 `c386914`。`npm run verify` 通过：40 文件 / **406** 用例
（基线 397，本次 +9）。五条判据全部在真实 Chrome 152 + 真实 `npm run build` 产物上实测，
并与**撤销修复的对照构建**逐条对比。

---

## 一、根因

### 现象

读到中段 → 刷新 → 阅读位置恢复 → 点侧栏目录某一章 → 页面纹丝不动；再点一次才跳。

### 机制

`useReadingPosition` 在增强（Shiki 上色 / Mermaid 出图）完成后会做一次位置校正，
理由是正当的：增强显著改变块高度，不校正落点就偏。这次校正只在两种情况下放弃——
文档是带锚点打开的（`anchorOpenRef` 闩锁），或者**用户自己滚动过**（`userScrolledRef`）。

问题出在第二条判据的**判定方式**上。`checkUserScrolled` 挂在容器的 `scroll` 事件上，
比对的是「实际 `scrollTop`」与「我们自己最后一次写入的 `scrollTop`」。而目录点击是
**程序化滚动**：`scrollToLine` 派发的是 CodeMirror 的 `scrollIntoView` 效果，真正的滚动
发生在它自己的测量周期里，`scroll` 事件因此排在很后面。同一次 dispatch 会**同步**触发
`update.viewportChanged`，`MarkdownEditor` 立刻 `enhanceMounted`，那批 Promise 在一个
微任务后落定并回调 `onEnhanced`——**校正跑在撤防之前**。

于是这一帧里发生的是：目录点击 dispatch 了一个「去第 18 章」的 scrollTarget，微任务里
校正又 dispatch 了一个「回到记录位置」的 scrollTarget，后者覆盖前者。CodeMirror 的测量
周期只看最后一个，两次滚动互相抵消，`scrollTop` 一动没动，`scroll` 事件也就无从发生，
撤防永远不会被触发。这解释了实测里最反直觉的一点：**不是「跳过去又被拽回来」，而是
从头到尾没有任何中间值**（4.8 秒内恒为 768）。

先手动滚 60px 就正常，是因为那次真实滚动让 `checkUserScrolled` 置了位。第二次点击能跳，
是因为第一次点击引发的高度/视口变化最终让 `scroll` 事件对不上期望值、把防撤掉了。

### 同一缺陷的第二条路径

`useRelativeLinks` 处理的正文 `[见下文](#某节)` 链接走的是完全相同的机制，因此有完全
相同的缺陷，而且更糟：`syncAnchorHash` 会把地址栏改成 `#第-18-章`，**页面却停在原处**，
分享出去的链接和屏幕上看到的内容对不上。对照构建实测复现（见第三节）。

## 二、修法与设计理由

### 判据的本质

撤防要表达的不是「用户滚了」，而是「用户已经明确表示要待在别处」。用户滚动只是这件事的
一种形态；**显式导航**（点目录、点正文锚点）是另一种，而且意图更强。旧代码只认前者，
所以判据太窄。

### 选定方案

在 `document.store` 里加一个单调自增的 `navigationEpoch` + `markNavigation()`，
由两条显式导航路径在**点击那一刻同步**自增；`useReadingPosition` 在每次「打开」开始时
存一份基线，把「序号变过」并入撤防判据 `isDisarmed()`。

```
TocPanel.handleSelect      ─┐
useRelativeLinks.handleAnchor ┴─> markNavigation() ──> navigationEpoch++
                                                          │
useReadingPosition: isDisarmed() = userScrolledRef ∨ (navigationEpoch ≠ 基线)
                     ├─ 首次恢复的 effect：撤了就不恢复
                     └─ onEnhanced 的校正：撤了就不校正
```

### 为什么是这个方案

**为什么放在 store 而不是回调 / context。** 目录面板挂在侧栏，是 `AppShell` 里与阅读页
并列的兄弟子树；`useReadingPosition` 挂在阅读页。两边传不了回调，除非新开一个 context
（像 `EditorContext` 那样）。而 store 本来就是这类「这一次打开是怎么发生的」状态的落脚处
（`openEpoch`、`pendingAnchor` 都在那儿），放这里不引入第二套机制，也不多一层 Provider。

**为什么是单调序号而不是布尔量。** 布尔量必须在「新的一次打开」里被抹掉，于是又多出一处
「抹除与置位谁先跑」的时序要求——闩锁栽过的正是这种坑（`anchorOpenRef` 的粘性缺陷）。
序号永不复位，谁关心「我在意的这段时间里有没有发生过导航」，谁自己存一份起点比对，
复位就等于重新取一次基线，不需要任何人按顺序去抹某个标志位。用例
「上一次打开里点过目录，不影响这一次打开的恢复」锁住了这条。

**为什么撤防必须在点击那一刻同步完成。** 这是从根因直接推出来的约束：任何「等一次测量」
「等一次事件」的撤防都会输给同一批块渲染派发的 `onEnhanced`。`markNavigation()` 因此写在
`scrollToLine` **之前**，而不是滚动落定之后。

**为什么不改成「校正前再量一次 scrollTop」。** 这是最省事的候选（`usePendingAnchor` 就是
这么做的），但对本缺陷无效：校正触发时 CodeMirror 的滚动**还没落定**，`scrollTop` 仍是
记录位置，值比对当场通过，校正照样把 scrollTarget 覆盖掉。实测的「恒为 768、没有中间值」
正是这条路走不通的证据。

**为什么地址栏锚点不调 `markNavigation`。** 它就是「这一次打开」本身，已经由 `anchorOpenRef`
按 `openEpoch` 闩住；再记一次只是同一个事实的第二份表述，还会让 `usePendingAnchor` 分不清
「别人导航了」和「我自己刚跳完」。已在 store 的注释里写明。

**为什么首次恢复也加这道守卫。** 恢复要等首轮块渲染完成（`view` 非空）才动手，用户完全
可能赶在这之前点目录；几百毫秒后再把他拽回上次读到的地方，和缺陷本身是同一种冒犯。
这一条不影响正常恢复：`markNavigation` 只在真的跳了（`view` 非空）时才调。

### 改了什么

| 文件 | 改动 |
| --- | --- |
| `src/stores/document.store.ts` | 新增 `navigationEpoch` + `markNavigation()` |
| `src/hooks/useReadingPosition.ts` | 新增 `navigationBaselineRef`（按 `openEpoch` 复位）与 `isDisarmed()`；首次恢复与 `onEnhanced` 都改用它 |
| `src/components/toc/TocPanel.tsx` | 目录点击时 `markNavigation()`（在 `scrollToLine` 之前、`if (view)` 之内） |
| `src/hooks/useRelativeLinks.ts` | 正文 `#锚点` 命中标题时同样 `markNavigation()` |

- 「没有导航时，增强完成后的校正照常生效」——正向对照，证明上面几条「没被拽回」不是因为

## 六、遇到的问题

1. **第一版复现脚本没能复现缺陷。** 刷新后等 6 秒再点目录，修复前后都正常。原因是那时
   增强早已完成、校正也已经发生，竞态窗口已经关闭。改成扫「点击延迟」才把窗口找出来：
   `shiki.md` 上是 **700~1500ms**，`mixed.md` 上是 **1000~1500ms**。这一点值得记下来——
   缺陷只在一个几百毫秒宽的窗口里发生，随手测一次很容易得出「修好了」或「本来就是好的」
   的错误结论。
2. **`Page.navigate` 到只有 hash 不同的同一 URL 不会重新加载。** 第一版回归 1/2 因此测了个
   寂寞（trail 恒定、Shiki span 数一模一样，页面根本没重载）。改成每次先 `about:blank`
   再导航才是真正的整页重开。
3. **Shiki 的上色用的是 CSS 变量而不是 `color`**（`--shiki-light` / `--shiki-dark`），
   最初用 `span[style*="color"]` 统计得到 0，差点误判成「增强没跑」。改成 `span[style]`
   后量到 1170 个，并核对了 `<pre class="shiki shiki-themes github-light github-dark">`
   与语言标签 `js`。
4. **顺带发现并修掉了第二条同源路径**（正文 `#锚点` 链接）。它比目录点击更难被发现，
   因为地址栏会被改成目标锚点、看上去像是跳了。

## 七、局限

- 与 8c/8d 相同：真实内容脚本未被执行（宿主页是逐行复刻）、`chrome.storage` 用 localStorage
  替身。这两处之外的一切——dist、渲染管线、Shiki/Mermaid、CodeMirror 的测量周期——都是真的。
- 竞态窗口的宽度与机器性能有关，实测数字来自本机 headless 1440×900。修复本身不依赖时序
  （撤防是同步的），因此窗口宽度不影响结论，但对照组失败的**具体延迟格子**在别的机器上
  可能不同。

## 〇、先说上一轮那个错误的结论 —— 教训比修复本身更值得留下

上一轮我在报告里写了这么一句：

> **额外核查**……「带锚点打开之后立刻点目录」：对照与修复后**都正常**（14593 → 2148），
> 因此本次**没有**动 `usePendingAnchor`，范围保持最小。

**这句话是错的，而且错在方法上，不是错在结论上。**

「立刻」= 点击延迟≈0。而**同一份报告的上一页就写着**：主判据的失败只出现在
700~1500ms，0/200/400ms 在对照构建上也照样通过。也就是说，我拿一个**已知落在窗口
之外**的延迟去测另一个同类竞态，然后把「没测到」当成了「不存在」。

**教训（请当成方法约束，不是感想）**：

> **实测证据必须落在缺陷的已知窗口内才算数。** 竞态类缺陷的「通过」只在被测延迟上成立，
> 不能外推到没测过的延迟。凡是同类竞态，**一律扫延迟**；而且不能假定两条路径的窗口
> 相同——这两条一个在 700\~1500ms，一个在 0\~200ms，正好错开。窗口的位置由「谁先跑完」
> 决定，不由直觉决定。

## 一、Important 1：统一 `usePendingAnchor` 的撤防判据

**问题**：`usePendingAnchor.onEnhanced` 判断「用户走没走」用的是「校正前现量一次
`scrollTop`」。这条判据认不出目录点击：点击派发的滚动要等 CodeMirror 的测量周期才落定，
而 `onEnhanced` 只隔一个微任务就到，此刻 `scrollTop` 还是我们自己写的那个值，
值比对当场判定「没走」，于是这一次重跳把刚点了目录的用户**拽回锚点**。

**改法**：给 `usePendingAnchor` 也加一份 `navigationBaselineRef`（同样按 `openEpoch` 复位），
在 `onEnhanced` 里**先判序号、后判值**。两条判据缺一不可，因为它们看得见的东西不一样：
显式导航只有序号看得见（值比对看不见它），用户手势只有值比对看得见（它不经过任何我们
能插桩的代码路径）。这一点写进了注释。

本 hook 自己的锚点跳转仍然**不**记导航（地址栏锚点就是「这一次打开」本身），
所以基线之后的任何一次自增都必然来自别人，语义干净。

## 二、Important 2：补上两个同类调用点 + 写明判定标准

**判定标准**（写在 `document.store.ts` 的 `navigationEpoch` 注释里，三条同时成立）：

1. **起因是用户的一次明确操作**——点击、快捷键、输入。页面自己的时序不算（增强后的校正、
   块渲染、自动刷新，那些是我们替用户做的事）。
2. **它真的把视口带到别处**——代码里确实执行了一次滚动。只改高亮、只写地址栏、
   或者目标本来就在视口里因而没滚，都不算。
3. **落点是我们自己算出来的**——正因如此，这段位移不属于「用户自己滚的」，值比对判据
   认不出它。

并明确加了一句反向说明：**不要**把第 3 条读成「只有 CodeMirror 的 `scrollIntoView` 才需要
记」。`scrollTo` / `Element.scrollIntoView` 这类会派发真实 `scroll` 事件的形式同样要记——
事件排在 `onEnhanced` 后面，指望它撤防一样来不及。外加「怎么记」（紧挨滚动那一行、
同一个同步流程里、没真滚就不要记）和当前调用点清单。

**新接的两处**：

- `useSearch`：跳到搜索命中。写在 `if (rect 不在视口内)` **之内**——目标本来就在视口里时
  这里不滚，也就不该撤防。
- `BackToTop`：返回顶部。写在 `if (!container) return` 之后。

**实测**：`shiki.md` 恢复到 5870/5882 后点「返回顶部」，对照与修复后**都**能滚到 0
（trail 逐段收敛 `5313 → 2300 → 960 → 382 → 110 → 5 → 0`，平滑滚动）。
**如实说明：这一处在本机窗口内没有观察到实际损坏**——平滑滚动派发的真实 `scroll` 事件
恰好抢在了校正前面。接线因此是**预防性**的（判据第 3 条明确要求这么做），效力由单元用例
保证，不是靠这次实测。`useSearch` 那处没有可直接点击的浏览器入口，只做了单元验证。

## 三、Important 3：合并两个 `onEnhanced` 的那段补上覆盖

`ReaderPage.tsx` 里那两行（`restoreAfterEnhance()` / `reanchorAfterEnhance()`）此前删掉
任何一行都全绿。新增 `describe('ReaderPage 合并两个 onEnhanced')` 三条用例，走真实接线
（`onViewReady` 交 view、`onEnhanced` 触发增强完成），其中第三条正是 Important 1 那个
危险组合的集成级锁——**它只在这段合并代码里成立**：两个消费方同时活着，才可能出现
「一个放弃了、另一个把用户拽走」。

## 四、Minor：订正 `TocPanel` 的过强归因

原注释写「`markNavigation` **必须**在 `scrollToLine` 之前」。核对 `MarkdownEditor.tsx`
的 `enhanceMounted`：`onEnhanced` 是在 `settleWithTimeout(...).then()` 里回调的，**恒隔至少
一个微任务**，所以同步路径上放前放后都来得及。已改成如实描述两条强弱不同的约束：

- **必须在这个同步流程里**（真正来不及的是「等滚动落定再撤防」）——放在滚动之前只是
  最不容易读错的写法；
- **必须在 `if (view)` 之内**（没跳就不该撤防）。

## 七、本轮遗留的顾虑

- `BackToTop` 那条接线在本机没有实测到实际损坏（见第二节）。它成立的依据是判定标准的
  第 3 条与单元用例，不是浏览器证据。若审查希望只保留有实测支撑的改动，这一处可以单拎
  出来讨论；我倾向于留着——判据既然写成了标准，就不该有满足标准却不接的调用点，
  否则下一个人读到的仍是一个「有例外但没说明例外」的抽象。
- 两条竞态的窗口位置不同（0\~200ms 与 700\~1500ms），且都与机器性能有关。修复本身不依赖
  时序（撤防是同步的），但**将来复核时不能沿用本报告里的具体延迟格子**，要重新扫。

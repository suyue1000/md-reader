# Task 8c: 定位机制修复（计划外任务）

这个任务不在原计划里。它由三个已确认的缺陷构成，都属于「定位 / 导航」子系统。

**按下面的顺序做**——第一项修好之前，另外两项没法可靠验证。

---

## 缺陷一（Critical）：带代码块的文档里，滚动定位完全失效

**现象**：文档里只要有 fenced 代码块，`scrollToLine` 对**尚未渲染**的目标完全不起作用——`scrollTop` 一动不动。CodeMirror 自己会在控制台打出 `Viewport failed to stabilize`。

**这是在 HEAD 上复现确认的既有缺陷**，不是哪个任务新引入的。上一个任务的实现者 stash 掉全部改动后在干净的 HEAD 上重现了它。

**诊断**：`src/editor/live-preview.ts` 里的 `class BlockWidget` 没有实现 `estimatedHeight`。

CodeMirror 需要估算视口外内容的高度才能决定滚到哪里。`WidgetType.estimatedHeight` 默认返回 -1（表示"不知道"），此时 CodeMirror 只能按源码行数 × 行高去猜。而块 widget 的渲染高度与源码行数的关系可能差得离谱——一个 20 行的 fenced 代码块渲染后可能只有 8 行高，一个单行的 `![](img.png)` 渲染后可能有 300px 高。估算错得太多，CodeMirror 反复测量也收敛不了，于是放弃滚动。

**影响面比表面更大**：所有 `scrollToLine` 的消费者都中招——
- 目录点击跳转（Task 8 记录为「已修复」，实际在带代码块的文档上仍不可用）
- 地址栏锚点跳转
- 正文里的 `#锚点` 链接
- 阅读位置恢复

而带代码块几乎是本项目目标文档的常态（README、技术笔记）。

**要求**：给 `BlockWidget` 实现 `estimatedHeight`。

怎么估是这一步的全部难点，请自己判断，但有几条约束：
- 估算必须**便宜**。它会被频繁调用，不能每次去测真实 DOM。
- 块缓存（`src/editor/block-cache.ts`）里已经有真实的 DOM 节点。如果某块已经渲染过，它的真实高度是已知的——这是比任何猜测都准的信息源，考虑用上。
- 没渲染过的块只能猜。按块的类型（代码块 / 图片 / 表格 / 段落）分别给经验值，会比统一按行数猜准得多。
- 估错不会导致错误结果，只会导致滚动位置需要二次校正。所以宁可给一个**粗糙但量级正确**的估计，也不要为了精确而变慢。

**验证**：必须在带 fenced 代码块的文档上实测目录点击跳转真的生效。这是本项缺陷的直接判据。

## 缺陷二（Important）：跳转不更新地址栏 hash

**现状**：目录点击（Task 8 引入）与正文锚点链接（上一个任务扩展）都不再更新地址栏的 hash。

**为什么这是个问题**：这个项目有一条明确宣传的设计——用浏览器直接打开 `.md` 时，阅读器跑在 `file://` 页面的 iframe 里，**地址栏保持为原始的 `file:///…/xxx.md#锚点`**，这样书签、分享出去的链接、页面内相对链接才不会失效。去读 `src/content/index.ts` 顶部的注释，那里写了为什么不重定向到 `viewer.html`。

hash 不更新意味着：用户跳到某一节之后复制地址栏分享出去，对方打开会落在文档开头。这与上面那条承诺直接冲突。

**已确认的边界**（审查者核实过，不必重新调查）：宿主侧一直只用 `history.replaceState`（`src/content/index.ts:218`），从未支持浏览器前进/后退，所以**这块没有增量损失**。要修的只是「地址栏反映当前位置」。

**要求**：让三条跳转路径（侧栏目录点击、地址栏锚点、正文 `#锚点` 链接）都同步更新 hash。

**注意上一个实现者指出的坑**：直接 `location.hash = xxx` 会触发浏览器原生跳转，和已经算好的精确落点打架。需要用不触发跳转的方式更新地址栏，并且嵌入模式下要经由既有的 `postToHost` 通道同步给宿主页面。

## 缺陷三（Important）：闩锁是「粘」的

**现象**：同一份文档，先带 `#锚点` 打开，之后不带锚点重新打开，阅读位置恢复会被继续挡住。已实测复现。

**成因**：`src/hooks/useReadingPosition.ts` 里的 `anchorDocRef` 闩锁存的是 documentId，用来表示「这篇文档是带锚点打开的，别用阅读位置覆盖锚点」。但它只在换**别的**文档时才失效——同一文档重开时 documentId 没变，闩锁还认为锚点优先。

**要求**：让闩锁在「同一文档重新打开且这次没带锚点」时正确复位。

**这里要格外小心**：闩锁本身是上上个任务为修一个隐蔽缺陷加的——带锚点打开一篇读过的文档时，增强完成后的位置校正会把用户显式指定的锚点**整个拽回上次读到的位置**。修复粘性时**绝不能把这个缺陷放回来**。

去读闩锁那段的注释，理解它为什么存在，再动手。

## 验收判据（硬要求）

`npm run verify` 通过**不等于**这三条修好了。这个项目已经吃过三次这个亏：目录高亮、锚点跳转、锚点被位置覆盖，全都是测试全绿而功能是坏的，最后在浏览器里才发现。

必须实测：

1. **带 fenced 代码块的文档**，点击目录跳到视口外的章节 → 真的跳过去了。（缺陷一的直接判据）
2. **带 Shiki 代码块的文档**上，锚点跳转落点正确、侧栏高亮正确。
   —— 这条是补验一个**已知盲区**：上一个任务因为被缺陷一阻塞，实测被迫改用 Mermaid 替代 Shiki，Shiki 这条路径至今没人验过。
3. 跳转后地址栏 hash 反映当前位置；嵌入模式（浏览器直开 `.md`）下宿主页面的地址栏同样更新。
4. **回归**：同一文档先带锚点打开、再不带锚点重开，阅读位置恢复正常工作。
5. **回归**：带锚点打开一篇**读过的**、含 Shiki 或 Mermaid 的文档，落点仍是锚点而不是上次读到的位置（闩锁没被弄坏）。

`fixtures/` 里有样例文档。如果能用 headless Chrome 实测（不引入新依赖、不联网），把观察到的具体数字写进报告；确实做不到就明确说明验到哪一步，**不要含糊地说「应该可以了」**。

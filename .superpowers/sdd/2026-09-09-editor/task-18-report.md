## 二、两条合规事项怎么处理的

### (1) `STORE.md:144` 的「只读」表述

原文：「用途说明必须写清楚『只读用户主动打开的文件及其所在目录』。」这句话在新增编辑能力之后是假的，已删除「只读」两字，改写为：

- `host_permissions: file:///*` 的用途说明本身只讲读取（这条没有变化，因为写入确实不是这条 manifest 权限带来的能力）；
- 新增一节「文件写入（File System Access API，不在 manifest 权限清单里）」，如实说明：写入是浏览器原生 API 在用户手势（进入编辑态、保存）下另外弹出的授权，不是 manifest 声明的权限；写入目标只能是用户已经主动打开、正在读的那份文件；用户拒绝写入权限不影响继续编辑，只是保存退化为「另存为」；「浏览器直接打开 .md」入口下的阅读器是跨源 iframe，拿不到句柄也弹不出选择器，编辑后无法写回原文件；
- 在「六、已知的审核关注点」里加了一句提醒：审核如果追问写入能力，这段说明也要一并准备好，因为它作用在同一份文件上，大概率会被一并问到。

这一条我判断需要独立成节而不是塞进 `host_permissions` 那条里，理由是它们的权限来源不同（manifest 权限 vs. 运行时 Web API 授权），审核在追问时也很可能是两条分开问，分开写清楚更不容易被追问到答不上来。

### (2) `STORE.md:53` 的 `storage` 用途说明遗漏编辑设置

已把 Task 12 新增的六项编辑设置（`autoSave`、`autoSaveDelay`、`defaultMode`、`showLineNumbers`、`tabSize`/`indentWithTabs`、`keepVersions`）补进用途说明，并额外加了一句区分：`storage` 里存的是这些设置的**数值**，不包含文档内容本身；编辑时的历史版本（`versions.ts` 的环形缓冲）只在内存里，不写入 `storage`，刷新页面即丢失——这一点如果不说清楚，审核完全有理由怀疑「版本保留数」这个设置项意味着扩展在存文档快照。

## 三、发现的其它与新能力不符的对外声明

- `README.md:35`（功能表「自动刷新」）与 `STORE.md:30`（详细描述里的同一条）都写着「用别的编辑器改完文件保存」。现在扩展自己就是编辑器，这个说法在两个维度上过时：一是听起来像在暗示「本扩展不能编辑」，二是没有提到编辑器自己写回时不会触发这条提示（自写回环判定）。已改成「文件在别处被改动（脚本生成、`git checkout`、命令行编辑等）」这种不预设「别的编辑器」的说法，并各自补一句自写回环 / 冲突不会静默覆盖。
- 除了简报点名的两处，`README.md`、`STORE.md`、`package.json`、`messages.json` 里再没有找到别的「只读」「阅读器」字样的定位性描述与新能力冲突（用 `grep -rn "只做一件事\|阅读器\|好看、好读"` 核对过，命中的都是「阅读」这个功能仍然成立的语境，不是排他性声明）。
- 隐私政策/详细描述里「不发起任何网络请求」「不上传」这条**核实后确认仍然成立**：保存与自动保存都是 `FileSystemFileHandle.createWritable()` / `write()` / `close()`，CodeMirror 全部本地打包，`versions.ts` 明确注释「不持久化是刻意选择，避免把用户文档历史写进本机存储越过零网络承诺边界」（见 `src/editor/versions.ts`、task-15-report.md）。这条承诺予以保留，且在 README/STORE 里都补了「编辑与保存同样不联网」的明确背书，而不是让读者自己去猜。
